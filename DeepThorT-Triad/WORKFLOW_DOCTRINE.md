# DeepThorTriad intelligent operating doctrine

Approved by the owner, 26 November 2026. Applies to Triad only; retain the separate original DeepThorT. This is an application-level authority and scheduling contract, not an assertion that every target capability has already been implemented.

## Responsibilities and authority

| Worker | Responsibility | Boundary |
|---|---|---|
| JANUS / SmolLM3 | Executive planning, decomposition, prioritisation, dependency coordination, delegation and recovery | Cannot expand the user's project grant or accept its own work as independently verified |
| Sentinel / Qwen3 | Independent specification, risk, evidence and quality review; precise correction advice | Cannot rewrite the user's authoritative requirements or grant permissions |
| Granite / Granite 4.1 | Software implementation, integration, testing and repair | Work only on scoped assignments and interfaces; request missing assets/tools |
| Gemma / Gemma 4 | Multimedia reasoning and production (art, music, video, textures, 3D, documents) | Use actual admitted production tools; return verified staged artifacts or blockers |
| Memory / Qwen2.5 | Independent recall, relevance, consolidation, anticipatory research and advice | Historical evidence never grants authority; optional recall does not gate foreground work |

All workers preserve original instructions and amendments, obey granted scope, avoid fabricated completion, distinguish observations from proposals, report blockers, use appropriate tools and requested output schemas. The native role-binding module is host-owned and versioned. Each worker receives its own responsibilities and team map; task instructions are preserved. This does not make a model prompt an enforcement boundary: host authorization, file and tool checks, independent review and OS caps remain authoritative.

## Workflow rules and target architecture

1. User goal and exact amendments are durable and authoritative. Determine intent: answer, research, create, repair, modify or verify. Act when asked to act, within existing grants.
2. JANUS maintains a task/dependency graph, interface contracts, milestones and acceptance requirements. Schedule independent ready nodes concurrently where resources and existing permissions allow.
3. Each role has an independent inbox/outbox. Bind task to requester, assignee, project/chat/specification revision, scope, dependencies, expected artifacts and acceptance. Replies and evidence cannot create new execution authority.
4. Priorities: cancellation/resource safety/serious defects; current user amendments; blocking dependencies; production and required tests; quality improvements; optional memory/research. Age waiting work to avoid starvation. Continue other ready branches when a dependency is blocked.
5. Resources: keep one shared hard 50% CPU/up-to-65% RAM-sized aggregate commit ceiling, 10% foreground RAM reserve and lower cap at startup under pressure. Use measured admissions, gaming priority and bounded queues, not five fixed CPU allocations. Defer background tasks first. Benchmark actual concurrency before raising per-model threads or adjusting resource weights.
6. Sentinel's review depth should be proportional to risk and uncertainty, while retaining mandatory review and real tests. Deterministic schema/hash/syntax checks do not require model reasoning. Review exact changed evidence; do not weaken approval or final acceptance.
7. Memory operates asynchronously, sends scope-bound, fresh advisory findings to JANUS/Sentinel at existing checkpoints and never waits for recall on the main path. Later add anticipatory retrieval of upcoming dependencies and controlled consolidation of observed knowledge.
8. Diagnose actual failures, distinguish source/format/tool/resource/permission causes, choose a different justified approach after bounded retries, test and checkpoint. Never repeatedly execute an unknown or interrupted side effect.
9. Integrate media/document/software tasks by real artifact contracts and inspectable receipts. Whole-game acceptance includes gameplay, actual engine imports, editable assets, sound/music, tests, docs and a runnable package.
10. Self-development: inspect exact source, stage improvements in isolation, run regression and independent acceptance, prepare a versioned update with rollback. Installation requires user approval. Preserve supervisory code, resource protections and original project authority.
