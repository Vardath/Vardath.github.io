# Vardath Bible — 88-Book Reference and Continuation Rules

## NON-NEGOTIABLE CONTINUATION RULE

**The end of `book/VARDATH-BIBLE.md` is the sole authority for progress.**

Whenever the user says **“continue”**:

1. Fetch and inspect the actual end of `book/VARDATH-BIBLE.md`.
2. Determine the last fully inserted book/chapter/verse from that file itself.
3. Continue directly from that point.
4. Do **not** use remembered checkpoints, chat summaries, progress claims, or this file's status notes as the authority.
5. Do **not** redo earlier material merely because chat history has been lost or condensed.
6. After every append/update, fetch the end of `book/VARDATH-BIBLE.md` again and verify that the new material is present and complete.
7. If a write stops part-way through a book, the actual final verse at the end of the manuscript determines the restart point.
8. Never place placeholders for later books after unfinished text in `VARDATH-BIBLE.md`; the physical end of the manuscript must remain a truthful progress marker.

This rule exists specifically so context-window resets, freezes, or lost messages do not cause duplicated work.

## LARGE-MANUSCRIPT TAIL RULE

As `book/VARDATH-BIBLE.md` grows, GitHub's normal contents/file endpoint may stop returning its text once the manuscript exceeds the endpoint's practical size limit. An empty or missing payload from that endpoint **must never be interpreted as an empty manuscript, a lost manuscript, or an unknown progress state**.

When the normal file fetch can no longer return the manuscript text:

1. Resolve the repository's current default-branch HEAD commit.
2. Read that commit's Git tree (recursively if necessary) and locate the tree entry for `book/VARDATH-BIBLE.md`.
3. Take the blob SHA from that exact tree entry.
4. Read the manuscript through GitHub's Git-blob endpoint using that blob SHA.
5. Inspect the literal end of the returned blob text. **That blob ending is the physical manuscript end and remains the sole progress authority.**
6. Before any append, verify that the expected last book/chapter/verse or final sentence is still the blob's actual ending.
7. After every write, resolve the new commit/tree/blob and inspect the new blob ending again.
8. If the normal contents endpoint returns an empty result because the file is too large, do **not** fall back to chat memory, checkpoints, this reference file, or a guessed line range.
9. For writes beyond the contents endpoint's size limit, use Git data operations (blob → tree → commit → branch ref) when necessary, while preserving the same pre-write and post-write physical-end verification.
10. A future GPT chat should use this Git-tree/blob method automatically whenever ordinary file fetching no longer returns `VARDATH-BIBLE.md`.

## LARGE-MANUSCRIPT APPEND RULE

Once `book/VARDATH-BIBLE.md` becomes too large for direct whole-file replacement through the connected GitHub write API, use the repository's deterministic staged-append workflow instead of attempting to resend the entire manuscript.

The installed workflow is:

`.github/workflows/append-vardath-bible.yml`

It watches for exactly one staging file matching:

`bible-staging/vardath-bible-*.md`

Required procedure:

1. Inspect the current physical manuscript end through the Git tree/blob method above.
2. Record the exact current manuscript blob SHA.
3. Build only the new contiguous Bible text that belongs after the current end.
4. Create one staging file whose **first line** is exactly:
   `<!-- EXPECT-BLOB-SHA:<current-manuscript-blob-sha> -->`
5. Put the Bible text to append after that first line.
6. The workflow checks `git rev-parse HEAD:book/VARDATH-BIBLE.md` against the expected blob SHA. If they differ, it fails instead of appending stale or duplicate material.
7. If the SHA matches, the workflow appends the staged text to `book/VARDATH-BIBLE.md`, deletes the staging file, commits, and pushes.
8. Use only **one staged Bible payload at a time**. Do not queue overlapping Bible append runs.
9. After the workflow commit appears, resolve the new tree/blob and inspect the literal manuscript ending again before continuing.
10. Treat the workflow as a deterministic transport mechanism only, not as research automation and not as a progress authority.
11. If a staged run fails, do not blindly rerun it. Re-read the current manuscript blob, rebuild the expected SHA if necessary, and stage only text that is still missing.
12. The staging file and workflow status never override the manuscript itself: **the literal physical end of `book/VARDATH-BIBLE.md` remains the sole progress authority.**

## FILE-ROLE RULE — NO PROGRESS LEDGER HERE

**This file does not record construction progress and must never be used to determine where the manuscript is up to.**

- Do not add or maintain current-book, current-chapter, current-verse, “inserted so far”, “in progress”, checkpoint, or completion-status fields in this file.
- Do not infer manuscript progress from source notes, historical comments, chat memory, commits, or anything else in this file.
- The **only** progress marker is the literal physical end of `book/VARDATH-BIBLE.md`.
- During ordinary Bible construction, the **only file to append is `book/VARDATH-BIBLE.md`**.
- `book/88.md` is a fixed directive/reference file for the 88-book order and operating rules. Do not append construction progress or source notes to it, and do not edit it unless the user explicitly instructs you to edit it.
- If this reference itself ever needs a deliberate correction, edit the relevant existing wording rather than adding a running progress log.

## LIMITED-AUTOMATION RULE

For this Bible project, browser/autonomous workflows are strictly subordinate to the manuscript and must be kept short so freezes cannot cause lost or repeated work.

1. Prefer direct source fetch/search over browser automation whenever possible.
2. Use **only one Bible-related autonomous run at a time**.
3. Scope any autonomous run to a **small, bounded task**: normally one source check, one page range, or at most a few chapters.
4. Set a short run budget where the tool permits it; do not launch long multi-page/multi-book crawls.
5. As soon as a run produces usable Bible text that belongs in the manuscript, **append/commit it immediately to `book/VARDATH-BIBLE.md`** before doing more work. Do not create or update a progress record in this file.
6. After every such append, fetch the physical end of `book/VARDATH-BIBLE.md` and verify it.
7. If an autonomous run fails, times out, freezes, or returns no usable result, **do not automatically rerun it**. Record the failure if relevant, re-check the manuscript end, and switch to a simpler/direct method.
8. Never treat an unfinished autonomous run, browser state, chat memory, or a planned task as completed Bible progress.
9. Do not accumulate uncommitted translation or transcription across many chapters. Work in small committed passes.
10. When the user says **continue**, first inspect the actual manuscript end, then inspect only any Bible-related workflow results that completed since the last manuscript append. Append verified Bible text to `book/VARDATH-BIBLE.md`, then continue sequentially.

### FIXED-ORDER REVISION SAFEGUARD

If the user explicitly changes the fixed 88-book order after later books have already been inserted, preserve the later completed material but repair the resulting earlier gap before ordinary tail-based continuation resumes. A user-directed list revision is the one exception where the physical tail alone cannot prove that every earlier required book is present. Remove books that no longer belong, update the contents/order, and insert the newly required replacement books in their numbered positions before advancing beyond the existing tail. Do not delete later completed books merely to restore sequential construction.


## FRESH-TRANSLATION WORKFLOW RULE — CHATGPT TRANSLATES, GITHUB ONLY STORES

For every book or section requiring a fresh Vardath translation:

1. **ChatGPT itself performs the translation in the active conversation.**
2. GitHub, GitHub Actions, repository scripts, staging workflows, bots, code, or automation must **never translate, paraphrase, rewrite, transform, assemble, or generate the English translation**.
3. A lawful source text may be retrieved from a repository or other source location, but once the source section has been retrieved, the translation step is done by ChatGPT here, directly from that source.
4. Do not use a script to turn the source language into English. Do not use repository automation to infer, compose, or rewrite translated verses.
5. Translation should be done in bounded sections small enough for careful human-readable review against the source.
6. Only **after ChatGPT has finished writing the English translation** may GitHub be used as transport/storage to append that already-finished text to `book/VARDATH-BIBLE.md`.
7. The staging workflow may concatenate the finished text into the manuscript, but it must not alter, generate, translate, or paraphrase that text.
8. If a future GPT chat begins translating a source and starts using GitHub or code as part of the translation process itself, stop and return to this rule: **translate here first; store later.**

## SPEED / CHUNKING RULE

Use the fastest safe construction method that preserves source integrity and the manuscript-end safeguard.

1. When a rights-safe English text is already established and does not require fresh translation, prefer **whole-book imports** or **large contiguous sections** instead of tiny chapter-by-chapter passes.
2. For long works where a single whole-book write would be unwieldy, use large bounded sections, normally about **10–30 chapters at a time**, or another similarly substantial natural division.
3. Canonical books using the established World English Bible Updated source may be imported in especially large passes, including a whole book where practical.
4. Once a source edition and rights basis have already been established for a book, do not repeatedly re-research or re-prove them before every append unless a genuine source problem appears.
5. If a usable public-domain or otherwise commercially reusable English translation exists, preserve that edition's wording subject only to the project's stated cleanup/editorial treatment and import it in large passes.
6. If no suitable English translation can legally be reused and a **fresh Vardath translation must be prepared**, translate it personally in the current ChatGPT conversation from the lawful source in **smaller verified sections**. **Do not delegate translation to GitHub, GitHub Actions, scripts, autonomous workflows, repository bots, or pre-generated machine translations.** GitHub may be used to retrieve the lawful source text and to store/append the finished Vardath translation, but the translation itself must be produced here by ChatGPT. Do not rush a fresh translation merely to increase throughput.
7. Fresh-translation sections must be large enough to make useful progress but small enough to compare against the source, resolve variants, and verify before the next section.
8. Regardless of chunk size, always inspect the literal end of `book/VARDATH-BIBLE.md` before writing and fetch it again after the write to verify the new physical endpoint.
9. A freeze or context loss never justifies redoing material already present at the manuscript end. Resume from the actual file.
10. These chunking rules change speed, not authority: **the literal physical end of `book/VARDATH-BIBLE.md` remains the sole progress marker.**

## Publication / rights rule

Before inserting a source text, verify that the exact edition/translation is one of:

- public domain;
- explicitly licensed for commercial republication and modification as needed; or
- an original translation/text prepared for this edition from a lawful source.

Use the source, translator/editor, publication date, and rights basis recorded in `book/source notes.md` as reference. If rights are uncertain, **do not insert that translation**; locate a legally usable edition or prepare an original translation. Do not turn this file into a running construction ledger or source ledger.

The working canonical base is the **World English Bible Updated (WEBU)**. eBible.org states that the World English Bible is in the public domain and may be copied, published, redistributed and sold. The name “World English Bible” is a trademark, so this compilation remains titled **The Vardath Bible**.
