# Crystal commerce — 0.3.3 development

This release implements the user's revised request: crystal miners operate away from the player using **custom simulated mining and sales**, with money paid to the player. The previous active-sector-following fallback is removed. This is not a claim that X4 simulates physical crystal deposits out of sector.

## Actual implementation

- All normal player S/M/L/XL ships with an installed turret or forward weapon can undertake the job. It needs no mineral hold, mining beam, collector drone, crew berth or captain-inventory capacity for simulated batches. Existing weapon/ammunition limitations still apply to the physical path.
- Range 99 uses the connected accessible galaxy. Existing home/range/risk restrictions and native travel blacklists apply. Empty sectors are filtered using native ore/silicon yield data when choosing another search sector. No destination is chosen from the player's position.
- When the ship is outside the player's sector **and** below visible attention, native `find_closest_resource` locates an ore/silicon field. The ship actually travels to it with native movement and must arrive within the field tolerance. Dangerous resource regions are excluded by the finder. There is no remote mining from a dock or while merely travelling.
- The default batch takes **five game minutes** of active operation and requests **24 crystal items**. Both are normal Behaviour settings: 1–30 minutes and 1–60 items. Time is stored per ship; only bounded ten-second active ticks count. Direct orders, travel, sales and time away from the saved worker cannot produce a large catch-up payout. Existing progress resumes at the same permitted field after interruption; player arrival suspends the abstract path.
- After the work, native `deplete_yield` drains **100 ore/silicon units per requested item** from the actual field, omitting the cargo container. Its in/out `amount` reports the quantity actually removed. Only whole hundreds of that actual quantity become sale stock. Zero yield means zero output; partial depletion caps output. Multiple ships compete for the same native finite resource pool. There is no synthetic crystal crate, physical deposit damage or player-inventory addition in this path.
- Conversion to crystal inventory families is custom, not the game's crystal spawn distribution: per item 85% `inv_crystal_01`, 12% `_02`, 2.5% `_03`, 0.4% `_04`, 0.1% `_05`. The five native ware definitions and prices are used. This is an explicit balancing abstraction of crystal prospecting, rather than ordinary ore placed in a solid hold.
- In visible simulation, the existing real crystal detection, forward/turret aiming, firing and native drop collection path remains. Actual removed captain-held crystals become sale stock. If native pickup routes the current drop into player inventory, only its observed, per-ware, drop-bounded new quantity can be withdrawn into stock. Pre-existing player inventory and unrelated items are not swept. Inventory Collector remains installed; collector competition and actual weapon/drop effects still need live verification.
- Positive sale stock takes priority over more mining. The ship selects a reachable, non-player faction station with a suitable dock and walkable interior, travels, **actually docks**, and spends ten seconds there before the simulated inventory-trader transaction. No physical trader NPC is spawned and no native barter offer or NPC account transfer is claimed. Failed docking retains stock and temporarily avoids that buyer.
- Sales quote the five native wares' current average prices. Native 9.00 baseline prices are 1,000 / 10,000 / 15,000 / 20,000 / 125,000 Cr, respectively; other extensions can change them. Zero-priced wares remain unsold. The finite stock manifest is moved into a saved sale claim before payment. Native `reward_player` supplies the simulated proceeds; only the observed positive player-balance delta reduces the unpaid claim and enters receipts. A rejected or partial credit retries **only its unpaid remainder**. Sale IDs prevent duplicate stock consumption, sold totals and reputation.
- A fully paid eligible foreign-faction sale grants a small **0.00002 internal relation** improvement, sharing the existing 30-game-minute faction cooldown with other services. No approach, failed sale or unpaid batch grants reputation. Other occupations retain their existing verified-service/actual-morale gates.
- Sale credits create ordinary native `script_add` financial records, with the correct transaction matching type in the existing optional description adapter. Detailed `Vardath Payment` receipts and completion/activity reports use vanilla General Logbook. No new ledger screen or custom financial rows are introduced. Without the optional native description callback, the engine's ordinary ledger wording remains.

## Persistence and preservation

Work position/ware/time, per-family stock, sale ID/manifest, unpaid money and totals live in the persistent player-entity per-ship table. Order/worker version patches initialize new settings and safely refresh an active occupation default; player orders and deployed hacker crew are excluded from recovery. Existing passengers/itineraries, other job histories, crew, equipment, ship ownership and normal turret modes are retained. Previously delivered player crystals are not automatically sold or backpaid. Losing a miner can lose its unsold stock; this is not a remote guaranteed-income service.

Defaults are not forced over an explicitly disabled simulation setting. On old orders the label formerly called Follow active crystal simulation now means Simulate crystal mining off screen. If its new batch controls are absent, reselect the Crystal Miner default once. Orders already lost to Hold Position in older builds must be assigned manually; intentional Holds are preserved.

## References and verification

Inspected native 9.00 [`order.mining.collect.ship.xml`](https://github.com/ArtByunex/x4-foundation-artbyunex/blob/e3e8a345e5624db118bff3eb171b60b0993fcc2c/aiscripts/order.mining.collect.ship.xml) uses elapsed mining time and the in/out `deplete_yield` amount for off-screen mineral gathering. The published command metadata documents optional cargo container and actual drained amount (`common.xsd:26046`) and resource-field search (`common.xsd:26888`). Native [`wares.xml`](https://github.com/ArtByunex/x4-foundation-artbyunex/blob/e3e8a345e5624db118bff3eb171b60b0993fcc2c/libraries/wares.xml) supplies the five inventory families/prices. Native mining gather-rate depends on actual mining hardware; the custom crystal batch rate intentionally supports the user's combat ships instead.

Twenty-one new mocked/source checks execute the shipped depletion conversion, actual item withdrawal and sale settlement XML. They cover empty/partial/shared fields, all grades, rejected item removal, protected existing player inventory, failed docking, direct-order interruption, partial payment after serialized reload, zero prices, cooldowns and duplicate settlement. All 106 Python source/accounting contracts and 78 Lua menu/native-bridge mocks passed locally. Static checks passed for 62 XML files, documented command attributes and 113 script calls across 13 behaviours. All seven extension audits reported zero errors and zero warnings. The five-extension bundle was checked byte-for-byte against 151 source files. These are source/mocked results, not engine tests; GitHub CI repeats the relevant checks.

**No X4 runtime or matching installed schema is available here.** Mocks cannot prove the engine streams/locates a resource field, depletes it without a cargo container in this load order, navigates/docks, parses every expression, persists live stacks or records native credits. Those integration stages, visible crystal hits/drop consumption and collection with Inventory Collector are still unverified. They must not be presented as in-game success.

The user's earlier debug(7).log independently proves one 5,000,000 Cr tour and three 8,000 Cr patrol payments, totalling **5,024,000 Cr**. It predates this mining change and proves no crystal proceeds. The preceding [log review](LOG_REVIEW_0.3.2.md) lists other errors and the fixes already included.

## Reproducible live test

1. Fully exit X4, overwrite this extension in place, restart and load the existing save. Keep Protected UI and Inventory Collector. Assign Crystal Miner to an AI captain on a forward-only fighter and on a turret-equipped L/XL ship. Use range 99, simulation on, default five-minute/24-item batch. Stay in a different sector; do not lead or accompany the miners.
2. Verify normal travel to a permitted real asteroid resource field, increasing simulated-work seconds, then `Galactic Occupations: simulated crystal batch` / `GO crystal simulation:` with **actual drained yield** and new stock. Empty/forbidden fields must not produce stock. Check the ship is not following the player's sector changes.
3. Observe actual station arrival/docking, `GO crystal sale:` balance values and zero unpaid balance, a native incoming financial record, one General payment receipt, sold-item total and another mining cycle. Inventory should not increase from simulated batches. Compare actual money against the saved manifest's native prices, not the expected average random batch.
4. Save/load midway through mining, with unsold stock, travelling to the buyer, docked before settlement and just after payment. Issue a direct move/Hold order and later let the default resume. No double depletion, duplicate sale or large time-away payout should occur. Test a destroyed/hostile buyer and blocked route; stock/claim must survive failure.
5. Run two miners in the same field, test range 0 and a limited jump radius, and test cautious/aggressive territory. Try another player sector during work. Return visibly to test the real turret/forward-gun/drop path and then the same cash-sale flow. Compare captain/player inventory with Inventory Collector active to detect losses or duplicates.
6. Confirm normal turret modes, crew/equipment, the Forge's special gun, vanilla ledger/search/graph and all existing passengers remain intact. Keep the new full debug log if any stage fails; the key markers distinguish field arrival, depletion/stock, physical pickup and actual payment.
