# DeepThorT v50 — neural JANUS/Sentinel deliberation and automatic X4 reference workset

Date: 23 November 2026. Baseline: verified v49 release (commit 38e160c346b36330ca3a4ad0533c7806a0cd2694).

## Actual behavior

- Existing local Qwen2.5-Coder-1.5B-Instruct ONNX remains the sole neural model, hosted by the previously supervised Windows Job Object. JANUS and Sentinel retain their independent persistent eleven-core/seven-Fano-faculty deterministic societies; v50 adds separate *real inference calls* by the same local model in JANUS reasoning and Sentinel counter-analysis roles, not newly trained specialist neural networks.
- Only for indexed X4 roadmap corrections and after three consecutive failed validator improvements, JANUS now requests two testable approaches and their supporting evidence. Sentinel independently critiques the JANUS response, challenges any invented identifiers or compatibility assumption, and advises a narrower test. Each has its own persisted source-bound model response in `state/reasoning-council-v50.sqlite3`; both recommendations appear in the JANUS/Sentinel recommendation tables. Subsequent Qwen file correction receives bounded advisory context. All outputs are untrusted; X4 validator and original user approval still control completion/writes. The council is invoked at most once per correction invocation and may cost two *additional, sequential* local inference calls. This is not independent neural weights or proof of genuine superior model intelligence. Other tasks are not yet orchestrated by the council.
- Project file list in `D:\x4mods` is the chosen output workspace only. Verified game sources remain outside it (read-only). `project_source_view.py` picks up to 14 inspected, hashed PE macro/component, turret, weapon, storage, library and index XML references and displays them as child rows in the left project panel. Preview validates original SHA256 and rejects path escapes/symlinks. These source rows cannot be treated as writable project files. They can be hidden by right-click with a per-project persistent exclusion; no X4 file is moved, copied or altered.
- Selecting a folder whose basename contains `x4` now starts a bounded read-only X4 installation/reference lookup automatically while not gaming. Clicking `Auto-discover X4 sources` performs the same lookup for any workspace. It uses configured Steam/GOG-style installations and existing extracted XML in DeepThorT `reference/x4` and configured source folders. No full-drive scan or unapproved XRCatTool extraction. When only CAT/DAT catalogs are present and extracted XML has not yet been approved for extraction, source XML is explicitly unavailable; `D:\x4mods` is never substituted for the installed game.
- `Show all workspace files` defaults OFF for folders containing x4 in the name and ON for unrelated projects. With the filter on, only files declared by the current persisted model plan or approved job (or explicitly chosen for review) appear as editable project entries, plus separately inspected X4 sources. It does not delete or move irrelevant files. All actual files remain available under the toggle. Existing permanent user inspection exclusions are preserved.
- Asynchronous X4 source-discovery reports from a previous selected workspace cannot overwrite the current workspace's sidebar.

## Unchanged safeguards and limitations

- Existing 20% aggregate Windows CPU/commit cap across DeepThorT and supervised children; gaming-first policy, original Windows launcher, eight Tk tabs, local Node/Transformers.js ONNX model, JANUS and Sentinel process identity, state, references and project files all preserved. Council calls use same ONNX worker, no extra Llama/Ollama/cloud process or second 20% allocation.
- Natural-language council advice can be mistaken and is not an independently validated solution; actual X4 in-game verification still outstanding. Full v50 regression uses scripted Qwen replies, not an independently benchmarked live Qwen. Real Windows game path and extracted reference availability need verification on the user's own machine.
- Whether a previous Llama *model* performed better is not demonstrated; its exact model, context/quantization and controlled test outcomes are unavailable. A previously uncapped standalone process could be faster without being more accurate. This release does not switch model engines.
- Approved file writes still require existing scope and receipts; no new approval bypass. Project files and vanilla reference files must not be conflated. Windows UAC and software installation control unchanged.

## Physical-Windows acceptance

1. Close DeepThorT; back up `D:\deepthort\state` and extract v50 source ZIP over `D:\deepthort` without deleting the launcher, models, references, state, node modules or projects.
2. Select `D:\x4mods`. Confirm automatic scan locates real X4 installation and, where present, extracted PE XML. The project files may be empty before there is a plan; the relevant game reference group should populate when extracted XML is available. Click `Show all workspace files` to inspect unrelated existing project files.
3. Click a vanilla reference: preview says READ-ONLY and does not offer edits or attach it as an editable project file. Right-click hide: source remains unchanged on disk; restore via the existing restore menu.
4. Retry the saved Xenon PE indexed plan. After three unproductive corrections, look for separate JANUS hypothesis and Sentinel critique stages in Processes/JANUS & Sentinel and a fourth model correction guided by them. Verify it does not claim any X4 validator check closed without changed accepted source coverage.
5. Export diagnostics if the exact game folder/PE macro is missing, source rows remain absent despite extracted XML, model worker exits, or council guidance fails to close any of the nine criteria.
