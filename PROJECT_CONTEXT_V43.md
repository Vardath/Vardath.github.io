# DeepThorT v43 — post-install tool verification (23 November 2026)

## Scope and architecture

This pass continues from the **green v42 source release**. There is only one LLM,
**local Qwen2.5-Coder ONNX**, with unchanged `inference_server.mjs`, original
JANUS and Sentinel, original eight-tab desktop, original Windows launcher,
resource caps and user project directories. The installed binary, state,
models, cache, node_modules and projects are not replaced by the overlay.

The prior software workflow recorded a WinGet exit code but did not prove that
an executable was available. New `deepthort_local/tool_verification.py` finds
exact catalog executable names in PATH (including newly installed per-user
WinGet Links), bounded known folders, configured registry PATH and bounded
WinGet package directories. A registry-only uninstall entry is **not counted
as an available executable**.

For a fixed short list of known CLI applications (Python, Node.js, Git, Godot,
Blender, Java, FFmpeg, 7-Zip, Pandoc, LibreOffice and Inkscape), the verifier
runs only a hardcoded noninteractive version/help flag under the current user
with a 12-second timeout, captures an output digest and checks an expected
version pattern. There is no shell execution, custom model argument, arbitrary
network retrieval, UAC bypass or automatic desktop GUI launch. Tools without a
safe probe are labeled `located_only`, not `version_verified`.

After a successful catalog WinGet installation, version checks are queued,
serially, only while not gaming, paused or running project work. Evidence is
written to `state/tool-verification-v43.json` and shown in the Computer & Tools
inventory and Processes log. A verified executable's parent is added to the
**current desktop process** PATH so preexisting **approved, fixed-profile**
project tests can discover it. Godot additionally gets `GODOT_EXECUTABLE` when
none was explicitly configured. System/user registry and permanent PATH are
never changed by this feature. Existing project grants, graph readiness,
user-approval boundaries and bounded repair budgets still govern execution.

## Limits and genuine playtesting

**An executable/version response is not proof of publisher identity, official
origin, program correctness, successful engine build or in-game behaviour.**
The previous v42 run must not be represented as an installer or gameplay test.
Physical Windows WinGet/PATH/UAC and Qwen inference are not exercised on Linux
GitHub Actions CI. Game engine and GUI-only applications are not automatically
started by this release. Tests generated by projects still run as the user's
regular Windows account, not within a security sandbox.

See `PLAYTEST_ACCEPTANCE_V43.md` for the future acceptance contract spanning
Windows programs, Godot, Android APK, X4 Foundations and RimWorld. The first
actual game playtest needs per-platform adapters, a safe staging environment,
process/log observations, controlled input and objective acceptance criteria.

## Windows acceptance procedure

1. Close DeepThorT. Back up `D:\deepthort\state`. Extract the SOURCE OVERLAY
   into `D:\deepthort`; preserve existing launcher/model/state/projects.
2. Choose a test project, use Computer & Tools to scan, and inspect known tool
   locations and evidence. For a missing catalog tool, use the user's existing
   standing routine install permission or explicitly select catalog install.
3. After WinGet finishes, leave game/pause gates unblocked and check Processes:
   the installer exit must remain distinct from subsequent `version_verified`,
   `located_only`, `not_found` or `probe_failed` evidence.
4. Verify `state/tool-verification-v43.json` shows the exact executable path,
   version evidence and timestamp. If a supported binary is moved or altered,
   its old proof should display stale/changed in the next inventory scan.
5. With a previously approved Python/Godot project, observe whether fixed
   tests resume when the tool becomes available. A test failure is not a
   permission to install anything beyond the existing curated tool policy.
6. Export diagnostics for failures; note Windows UAC prompts, real game
   performance and any missing tool locations. Do not try actual mods in your
   main save/profile until a staging adapter has been implemented and tested.

## Next pass

v44 should implement an explicit, instrumented **run-and-observe acceptance
adapter** for one selected target (prefer Godot or a simple Windows program):
launch with controlled arguments, capture logs/exit status, collect observable
runtime assertions and screenshots, stop/retry/rollback without damaging the
normal installation. Add actual X4 and Android adapters as separate passes;
never confuse successful compilation or an app opening with gameplay success.
